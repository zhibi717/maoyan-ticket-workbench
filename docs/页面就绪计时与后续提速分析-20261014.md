# 页面就绪计时与后续提速分析

用户希望区分猫眼页面加载与脚本开销，并继续减少可控制的时间。本轮先分析已完成的杨千嬅11月21日、1098元、1张真机记录，再完善电脑模板；没有重新创建或取消订单，没有付款。

## 现有记录能证明什么

上一轮从入口点击至支付弹窗核实的总时间为5022ms：

| 页面转换阶段 | 等待与识别合计 | 其中控件读取调用的墙钟时间 |
|---|---:|---:|
| 入口 → 选票页 | 925ms | 393ms |
| 票档确认 → 订单页 | 1384ms | 797ms |
| 提交订单 → 支付弹窗 | 1934ms | 1164ms |
| 上述三段合计 | **4243ms** | **2354ms** |

4243ms约占全程84.5%，说明耗时主要发生在页面转换期间。但这些阶段也包含脚本读取、检查和轮询，不能把4243ms命名为猫眼纯加载时间。

包括选档和提交前核对，全程控件读取调用累计2893ms。这个时间已包含在5022ms内，不能与4243ms相加。读取调用也可能等待安卓无障碍响应，并不全部是可直接删掉的CPU计算。

现有记录缺少屏幕首帧显示、猫眼内部请求开始/结束和渲染完成时间。因此猫眼纯加载时间、服务器响应时间均保持未知，不能将剩余时间直接归给网络或服务器。此次没有用此前的页面布局或图片补造时间戳。

## 已加入的独立计时

新模板在既有读取与点击处记录`transitionTimings`，覆盖入口后页面、票档控件就绪、确认后订单页面、提交后支付页面。记录内容包括：

- 发出动作的时间与调用耗时。
- 最后一次观察到目标状态尚未就绪的时间。
- 首次观察到目标状态就绪时，该次读取的开始时间和观察完成时间。
- 实际执行下一次动作的时间，以及首次观察就绪至动作之间的差值。
- 阶段读取次数、读取调用累计墙钟时间、核对完成时间和完成状态。

只记录固定阶段、状态和相对时间，不增加页面查询，不保存姓名、手机号、证件或页面原文。首次观察到支付弹窗候选与随后金额、弹窗边界核对完成是不同的时间点。无法完成核对时保留未完成状态。

这些是无障碍控件的采样结果，不是页面内部加载或渲染时间。两次采样之间是否已有画面、控件树是否延后更新，仍不能由它们单独确定。若要独立检查画面首次显示，需要另行对齐录屏时间；录屏本身也可能影响手机性能。

## 已实现的进一步优化

1. 选档后等待票数、合计金额和确认按钮就绪的检查周期由80ms缩短为20ms，选择提示消失的等待由40ms缩短为20ms。读取已消耗整个周期时，仅额外让出2ms；页面已经就绪则立即处理，不固定睡满20ms。
2. 点击票档确认后等待订单页，首轮和后续轮询均只读当前文字。若旧选票页暂时仍在，不再补齐它的全部坐标与状态。确认已经点击一次，这些旧选票控件不会再次使用。
3. 到达订单页后，原有完整观演人检查与提交前的新快照核对继续保留；金额、日期、数量、验证码、支付边界和提交一次限制未移除。

上一轮订单等待的11次读取中，有2次完整读取。新的文字等待模式可以减少其中不必要的坐标与状态查询，但它不能加快猫眼的请求或页面更新，也不保证完整流程相应减少固定毫秒数。

当前保留的上一版为`autox/versions/maoyan_live_before_readiness_timing_20261014.js`，与此前实测入口20ms的模板一致。用户可以继续进行同条件对照。

## 验证

JavaScript语法检查通过，完整流程143项测试通过，用时46.487s。新增回归验证：

- 控件在模拟点击后96ms就绪时，新版在100ms确认、旧版在160ms确认；两者都没有在控件就绪前点击。这是采样逻辑验证，不是真机成绩。
- 页面已经就绪时，计时本身不增加整树读取次数；诊断只含固定阶段和数字，不含演出或私人页面文字。
- 确认后旧选票页仍暂时显示时，新版对旧页面的坐标查询为0，最终订单的观演人核对仍执行，提交仍为1次。
- 日期、金额、数量、验证码、观演人变化和支付停止边界继续通过现有测试。

## 尚需实测的部分

完成代码修改时，本轮新增计时与优化尚未同步手机。随后用户授权张智霖10月24日1280元测试，新版已同步并实际运行，完整到达支付弹窗，耗时5002ms。首次观察到就绪至票档点击52ms、确认点击62ms、订单提交点击116ms；订单等待没有完整读取旧选票页。详见`张智霖1280页面就绪真机测速-20261014.md`。

此前杨千嬅925ms/5022ms属于修改前的真机成绩。本轮总耗时与之仅相差20ms、与此前张智霖1080元4387ms相比反而增加615ms，不是受控A/B，不能认为全程获得明显提速，也没有测出猫眼内部纯加载时间。

下一轮应先看“首次观察到就绪 → 实际点击”的差值。如果这里较大，继续减少重复属性读取；如果这里很小而页面转换仍耗时较长，继续压缩本地点击调用的收益就有限。单次调用、模拟时钟或静态页面查询不能替代从入口到正确支付弹窗的完整测速。
