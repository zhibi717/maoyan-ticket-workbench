# 猫眼只读查询真机测速

用户授权只读取页面，不点击购票、不创建订单。起始手机位于设置页，打开猫眼后回到首页。启动AutoX测速脚本时的“运行脚本”按钮由电脑点击；测速脚本自身不包含点击、选档、订单提交或付款API。

当前现场是猫眼首页，不是选票或订单页。主页内容会更新，完整读取遇到缓存失效或属性获取开销，可能明显波动。测的是读取方法的成本，不是客户端或服务器页面跳转成本。

## 全部尝试

1. `read-only-1791895628`：首次完整读页未完成，脚本结束，没有可用样本。其错误细节不足，未推定具体原因。
2. `read-only-1791895829`：补充诊断后，确认失败阶段为`full_properties`，原有读页预算保护触发；未测到其余方法。
3. `read-only-1791896015`：修改只读基准的失败记录方式，达到预算的项目单独记失败并继续其他项目。正式购票脚本的保护上限未修改。购票标志在首页均不存在：3个文字查询中位数66 ms，7个140 ms；这些是缺失查询，不能当成按钮命中成绩。
4. `read-nav-1791896266`：使用首页实际出现的导航文字做命中对照，同一页交替执行6轮。保存首轮，后5轮用于中位数。

## 命中对照结果

| 方法 | 首轮 | 后5轮成功/失败 | 后5轮中位数 | 六轮已完成样本范围 |
|---|---:|---:|---:|---:|
| 整页完整属性 | 2035 ms预算停止 | 2/3 | 无可靠完整中位数 | 144–1674 ms，其余4轮超时 |
| 整页文字 | 2027 ms预算停止 | 1/4 | 无可靠完整中位数 | 唯一完成样本62 ms，其余5轮超时 |
| 原生定向查询3个文字 | 71 ms | 5/0 | **64 ms** | 55–71 ms |
| 原生定向查询7个文字 | 134 ms | 5/0 | **136 ms** | 123–146 ms |

3个查询文字为“首页、演出、我的”，每轮总共找到5个候选，其中4个文字或描述完全匹配。查询3个文字不等于得到3个唯一按钮，后续业务仍需去重和作用范围核对。

7个查询文字额外加入“搜索、佛山、电影、影院”，每轮总共12个候选，其中6个完全匹配。查询数、返回候选数量和业务操作数是不同指标。

完整读取的超时均触发2秒时间上限，没有触发1000节点上限。不能把其少量完成样本的中位数当成整页读取的典型耗时；原始运行结果中的成功子集中位数909 ms和62 ms没有计入超时，因此不用于正式比较。

## 能得到的结论

- 在本次猫眼首页环境中，少量原生定向查询全部完成，成本较稳定；反复复制整页的完成时间波动大，多次达到预算限制。
- 优先采用“少量阶段标志定向查询 → 命中后读取并核对业务所需控件”的设计，有真机读取性能依据。
- 没有验证开售时刻到点击的延迟、首次购票页出现时间或整段订单耗时。不能把64 ms或136 ms说成跳页时间，也不能声称100 ms内能进入购票页。
- 实际购票仍需核对演出、日期、金额、数量、观演人，以及阻塞/验证状态；这些不包含在导航文字查询基准中。
- 本次没有改正式购票流程，只更新独立只读基准的诊断和统计。下一步需要在选票页现场验证命中完整业务控件的成本，再判断哪些正式读取可以替换。
