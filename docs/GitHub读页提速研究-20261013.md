# GitHub读页提速研究

调查日期：2026-10-13。问题是如何减少定时开售后的触发延迟和页面识别耗时。研究没有验证几毫秒跳页，也没有创建、取消或支付新订单。

## 当前记录提供的线索

IEM成功轮次累计55次读页，根窗口获取319 ms、控件遍历复制4550 ms，共4869 ms。该累计统计还包括入口点击之前的检查；入口点击到识别支付弹窗5768 ms是另一个统计窗口，不能直接减去4550 ms得到潜在新成绩。

杨千嬅佛山1098元成功轮次为5023 ms。六哲466元轮次进入订单页3101 ms，完成“立即支付”调用3260 ms，但提交结果未确认。后者不能用于支付弹窗提速对比。

## 优先次序

1. **轻量识别页面更新。** 页面转换期间只定向查少量阶段标志，命中后获取需要核对的日期、金额、数量和控件关系。减少在加载期间重复复制整棵树。
2. **收缩选票页读取范围。** 定向查询目标日期/金额和按钮，再检查其父卡片和相邻数量、合计；保留同卡重复标签合并、不同卡片歧义保护。
3. **减少重复读取。** 同一次决定中共用一个短期快照，点击、事件变更或窗口变化后立即丢弃；提交前仍重新核对演出、金额、数量和观演人。
4. **事件驱动辅助唤醒。** 参考GKD，在窗口/内容变化事件到达时唤醒读取。事件只能作为变化信号，不跨线程保留可能被回收的事件对象或旧节点，也不能把事件时间当作画面呈现时间。原生模块需要正确注销监听、回退和实机验证。
5. **单独验证定时触发。** 提前启动与检查无障碍服务，记录预定时刻、开始点击、首个阶段标志和完整页面核对完成四个时点。修改循环间隔不等于整页跳转同样快。

第一、二项是目前最有源码和本机记录支持的方向。实际收益需要测量；应用和服务器处理时间不能由这个客户端优化消除。

## 快速模式的具体限制

AutoX v7.2.4缓存根节点在窗口状态变化或视图聚焦事件中更新。源码没有在该缓存更新分支中处理所有内容变化事件。在同一窗口内“已预约”变为“立即预订”时，直接依赖此缓存有读取旧状态的风险；风险是根据源码作出的推断，尚未针对本机这个转换验证。

当前主脚本直接调用`auto.service.getRootInActiveWindow()`。`auto.setMode("fast")`改变的是AccessibilityBridge的选择器根节点路径，单独修改模式不改变当前这行原生服务调用，不能作为已经生效的提速补丁。

## 准备的只读基准

文件：`autox/maoyan_read_benchmark.js`。整页读取基线来自本项目当前生产读页函数。

- 每轮交替比较整页完整属性、整页文字、3个阶段标志定向查询、7个定向查询。
- 每次从当前窗口取根，释放节点；不缓存上一轮节点。首轮结果单独保留，后5轮报告中位数和最大值。
- 只输出耗时、节点数量和匹配数量，不输出观演人、电话号码、证件或原始页面文字。
- 不含点击、选档、提交、付款代码，运行时给12秒返回猫眼。运行结果写在手机下载目录的`qiangpiao-read-benchmark-result.json`。
- 静态页面只读基准不代表第一次跳转时的冷读取成本，也不能代替正式开售场景测试。定向查询基准只用于识别性能研究，尚未包含完整购票校验，不能直接当成正式流程。

初次准备时USB未连接。用户随后连接并授权只读测试，已完成首页的缺失查询和实际导航文字命中对照：3个文字查询中位数64 ms，7个136 ms；整页读取多次触发2秒预算。完整结果、初次失败以及统计限制见[只读查询真机测速-20261013.md](只读查询真机测速-20261013.md)。没有真实开售跳页的新成绩，原正式购票流程未被本次研究修改。
